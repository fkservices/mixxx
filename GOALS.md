## Product we are planning

Build a desktop AI DJ app that runs on the same computer as **Mixxx**, sends and receives MIDI, and visibly operates the real Mixxx controls. The user supplies a Mixxx playlist; AI arranges its order and can perform the whole set enjoyably. Track selection, editable and saved set lists, physical-controller coexistence, live session visualization and JSON session history are part of this build.

**Current build excludes** Serato and other DJ hosts, Raspberry Pi deployment and a custom external AI box. These exclusions do not reduce the Mixxx feature coverage target. First runtime target is the local Mac and a frozen Mixxx version/skin; additional OS/skin profiles require separate evidence.

## Accepted decisions

- **Standing product preference:** wherever a choice offers both automatic AI decisions and user configuration/overrides, select that combination without repeating the question. Distinct unresolved tradeoffs still require discovery.
- **Track-order control:** AI chooses opener/closer unless the user pins them, and may adapt remaining order while respecting user pins and active-transition constraints (Round 1, questions 10–11, resolved by the standing preference).
- **Playlist synchronization:** let the user choose automatic updates from the original Mixxx playlist to the remaining set, or a starting snapshot kept until manual refresh. Automatic updates preserve the active transition; record source/plan revisions and user edits in session history. Delegated default: source snapshot until manual refresh (Round 1, question 16).
- **Set saving:** provide all three selectable behaviors: save in the app with optional creation of a new Mixxx playlist; automatically save both locally and as a new Mixxx playlist; or save locally with manual file export. Preserve the original playlist. Delegated default: local autosave with optional new Mixxx playlist (Round 1, question 17).
- **Track preparation:** reuse existing valid analysis, prepare the first few tracks and process missing analysis ahead during playback. Offer a prepare-everything-first setting and user overrides. Keep background preparation outside the MIDI event loop. Delegated defaults include per-feature override provenance and separate AI cue suggestions (Round 1, question 18).
- **Learning preferences:** learn locally over time from explicit ratings and saved preferences, set-list edits and manual mixing interventions. Retain the context/source of inferred preferences and distinguish temporary session adjustments from persistent musical preferences. Delegated defaults require inspectable preferences, correction, reset and disable controls (Round 1, question 19).
- **Musical quality:** balance natural transitions, an enjoyable whole-set journey and creative experimentation. The set should be fun to listen to without unintended tempo/beat mismatch or harmonic clashes. Validate technical execution and human listening quality together; a correct MIDI trace alone cannot establish a good mix (Round 1, question 20).

- **Use cases:** both private listening and live DJ sessions (Round 1, question 1).
- **Typical playlist size:** 10 or more songs (Round 1, question 3). Initial validation target is 250 occurrences; larger inputs receive a visible capacity assessment; smaller lists still need valid behavior.
- **Set duration:** approximately 10 minutes through multiple hours (Round 1, question 4). Offer AI-chosen duration, a user-entered time limit, and a user-entered duration range (Round 1, question 5). Support short mixes and long sessions; initial validation target extends to 6 hours, subject to measured capacity; infeasible all-song/time constraints require the user choice described below.
- **Song sections:** AI selects musically appropriate parts of each song rather than requiring full-file playback. Plan entry/exit points and transition lengths around the chosen duration policy while accounting for every playlist entry (Round 1, question 5).
- **Infeasible duration:** if the selected time limit/range cannot accommodate meaningful sections of all entries, flag the conflict and let the user choose before starting. Neither automatic-start mode nor the AI-choice preference permits silent omissions or duration changes (Round 1, question 12).
- **Existing cue integration:** use Mixxx cue points, hotcues and applicable intro/outro markers when selecting sections and transitions, and use the corresponding MIDI mappings to trigger supported actions. Preserve existing user markers. Verify access to stored cue positions/types/labels as well as MIDI triggering; do not assume raw MIDI contains the saved cue metadata (additional requirement at Round 1, question 12).
- **Mixing style:** AI chooses a suitable style from the music, with an option for the user to select a style instead (Round 1, question 6).
- **Tempo changes:** prefer small adjustments and normally allow up to moderate changes when useful. Let the user configure tempo limits; delegated numeric defaults prefer within 3% and normally cap at 6% (Round 1, question 7).
- **Energy flow:** AI plans energy automatically by default. Include energy presets and an editable custom energy curve in the set-planning UI (Round 1, question 8).
- **Starting an AI Only set:** offer review-first and automatic-start choices (Round 1, question 9). Automatic start is part of an explicitly initiated set workflow; it does not bypass global disarm or resume old actions after restart/reconnect.
- **Musical range:** open-format playlists may span any genre, era and tempo. Use BPM, harmonic compatibility and lyrical/vocal matching to choose tracks and transitions (Round 1, question 2). Delegated defaults prioritize confident hook/phrase handoffs with optional theme/language signals; local metadata, supplied timed lyrics and opt-in local transcription provide inputs, never MIDI alone.

- **Stack:** TypeScript/Node.js communicator and executor, native MIDI binding behind an interface, JavaScript mapping in Mixxx, TypeScript/HTML local desktop UI, and a separate local AI/analysis process. Mixxx plays audio. MIDI carries commands, metadata/state where implemented, and feedback, not audio.
- **Playlist behavior:** AI may rearrange the order. Preserve every playlist occurrence, including intentional duplicates, with no silent omission or replacement. Native Mixxx playlist selection and reliable track identity/load confirmation are required. Playlist file import can prove an early step but does not replace native access in the delivered build.
- **Music pool:** let the user choose per set between supplied-playlist-only selection and free selection from the local Mixxx library. In free selection, AI may add library tracks without per-track approval; show their origin in the planned/actual set and JSON history. This setting is independent of AI Only, B2B and Playlist Only performance modes. Preserve original playlist accounting and chosen time constraints; delegated default is supplied-playlist-only selection (Round 1, question 15, clarified by the user).
- **Duplicate tracks:** show a soft, non-blocking flag and retain repeated occurrences. Prefer appropriate sections not already played, using actual playback-section history and cue/phrase boundaries. This is a best-effort preference, not an absolute requirement to avoid all repeated material. Delegated default allows recent local history (30 days, configurable/off) as a soft signal (Round 1, question 13).
- **Unavailable tracks:** automatically skip missing, unreadable or unplayable entries and advance to the next playable song, including confirmed load failures during a set. Retain each occurrence and skip reason in the UI/session history; never mark a skip as played or delete it from the source playlist. Preserve ongoing playback where possible while preparing the next song. If none remain playable, end/report clearly without an endless retry loop. This explicit exception does not authorize omitting playable songs to fit a duration (Round 1, question 14).
- **Set management:** Preview and edit order, pin upcoming choices, save/load sets, preserve source playlist, track planned versus actual playback and incomplete/failed entries, and reconcile before resuming. “All songs” requires audible musical participation, not merely loading or briefly triggering each file. Define and validate the listening experience.
- **Startup mode:** remember the last selected performance mode, while keeping AI performance disarmed after launch. Do not restore queued actions or armed state; delegated first-launch default is B2B disarmed (Round 2, question 2).
- **Switching performance modes:** when already armed, switch between AI Only and B2B without another resume action. Cancel old-mode work, reconcile observed state and continue under the new authority rules. Switching modes never clears explicit disarm. Switching from Playlist Only to AI Only or B2B requests performance start after cancellation/reconciliation without another Start action. Distinguish suspension caused by Playlist Only from explicit disarm, which stays latched (Round 2, questions 6–7).
- **AI Only mode:** AI has performance authority while armed. It overrides ordinary manual knob changes promptly through smooth, valid, bounded recovery actions, without a B2B hold or waiting for the next transition. Global disarm and execution guards remain higher priority (Round 2, question 4).
- **B2B mode:** human input overrides AI on the affected controls for the rest of the current transition. Stop those AI writes immediately. The configurable quiet period defaults to 3 seconds, reset by continued input, but its expiry never returns ownership mid-transition. Reclaim at a later transition start only after release, quiet expiry and fresh state reconciliation; otherwise retain the hold. Begin new adjustments from the human value without restoring the abandoned curve. Respect touch/release where available and disclose value-only inference (Round 2, question 3 and user clarification).
- **B2B manual song replacement:** respect the human-selected new song and adapt the transition and remaining set around it. Cancel commands tied to the previous track, confirm current identity/state and preserve human control holds. Do not reload the old AI choice or falsely count its playlist occurrence as played. Delegated default retains the displaced occurrence for later unless explicitly skipped; preserve any already-played spans (Round 2, question 8).
- **Playlist Only mode:** AI organizes the playlist; the human mixes. No AI deck-load or live performance commands. Read-only host access and explicit playlist-save operations remain available.
- **Global disarm:** provide an always-visible on-screen button, keyboard shortcut and assignable MIDI-controller button, all independent of planner responsiveness. Disarm cancels future AI performance commands while music keeps playing and takes priority in every mode. Record input source and outcome. Explicit disarm, transport loss and restart require deliberate rearming; mode changes invalidate stale work (Round 2, question 5).
- **Physical controller:** A real MIDI controller connects directly to Mixxx alongside the virtual AI routes. Human inputs and actual host changes inform the AI. Preserve hardware mapping/pickup behavior and avoid feedback loops.
- **Available hardware:** user reports a basic MIDI controller and mentions Hercules and Reloop Buddy. Treat Reloop Buddy as a named candidate; confirm the exact Hercules model and primary fixture before hardware implementation/testing. Compatibility is not yet verified (Round 2, question 1).
- **Session capture:** Record AI intent, raw AI outbound MIDI, raw physical-controller input, decoded musical meaning, actual host observations, mode/ownership changes, track occurrences and timing. Preserve source/device/causal evidence and label uncertainty. Capture gaps must be explicit; do not claim lossless recording without evidence.
- **Session UI:** Live reader and historical reader share a timeline with track/deck layers, crossfade overlaps, action markers and parameter curves. Show labels such as bass down, volume up or jog backward, with raw bytes available on demand. Filter by AI/human/unknown source, device, track/deck, action and time.
- **History format:** Versioned JSON session export with a recoverable local event journal, snapshots and bounded handling of long sessions. Historical playback/scrubbing is visualization only and never resends MIDI. Audio/waveforms use separately prepared optional assets; MIDI is not an audio recording.
- **Quality and responsiveness:** Separate AI planning from timed execution. Measure host/UI/audio timing and control handover under realistic load. Compare recorded AI sets with a Mixxx AutoDJ baseline and obtain human listening review. No hard-real-time or subjective-enjoyment guarantee from unit tests.
- **Full Mixxx target:** Inventory all 22 researched feature families, then track command, feedback, native UI and runtime evidence independently. Add narrow host operations for gaps; no direct writes to Mixxx's live database. Unknown or unsupported capabilities remain visible in the denominator.

## Additional defaults selected under delegation

- Manual Pause/Stop latches a B2B deck transport hold until human playback or explicit release. Other independent deck work may continue. Control/deck pins are available until released.
- Respect human-loaded additions even when the AI music pool is playlist-restricted. Keep original occurrence accounting and record provenance.
- Use deterministic, validated fallback plans if the AI is late and state remains trustworthy. Lost essential feedback disarms; no stale-plan replay.
- Keep existing cues intact; AI section suggestions stay separate unless the user explicitly saves supported markers.
- Record session data automatically; master audio capture is opt-in. Preserve raw MIDI, semantic meaning, observations, uncertainty and explicit recording gaps.

4. Long builds, downloads, analysis and the uninterrupted 30-minute-or-longer set test use persistent jobs with separate launch, bounded observation and result-review assignments. An observation timeout never justifies restarting a live job.
5. Document safe parallel batches and exclusive leases for shared entrypoints, package manifests, Mixxx, physical controllers, MIDI routing and audio capture. Workers do not revert one another's edits.
6. Include repeatable per-capability tasks for the full inventory; their unknown eventual count is explicit. No single “implement all effects” or “test every feature” assignment hides unbounded work.
