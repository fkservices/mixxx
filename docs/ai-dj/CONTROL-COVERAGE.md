## Capability register

The generated [control declarations](../../res/controllers/mixxx-controls.d.ts) are a useful seed. Expand templates against actual deck, effect, stem, and sampler counts at runtime. Cross-check the selected host version's manual and inspect UI menus/preferences as well as the runtime controls; generated declarations include aliases and version-specific or read-only controls.

Each eventual capability record needs:

- Stable semantic ID, host version/profile, group/key or host operation.
- Read/write/trigger/momentary/relative semantics; valid range, units, scaling, and default.
- MIDI command and feedback encoding; capability prerequisites and active instance count.
- Preconditions, track/ownership generation, postcondition, deadline, and retry policy.
- Native UI element/panel, or required visibility extension.
- Source evidence, test case, runtime result, and unresolved limitations.

Track command support, feedback support, and UI visibility separately. Mark capabilities as `candidate`, `verified`, `extension-needed`, or `unresolved`. Never infer that a zero returned by a missing control means a valid disabled state.

## Closing the full-feature gap

1. Freeze a runtime version and UI configuration, then enumerate its controls and visible/modal operations. Treat the table above as starting categories.
2. Map all existing controllable functions through the normal control system, retaining native UI bindings.
3. For each gap, write a tiny host-facing operation specification: input, allowed state, existing service invoked, output, confirmation event, UI effect, and cancellation behavior.
4. Expose those operations through the custom MIDI mapping/protocol. Adding an arbitrary SysEx opcode alone does not create host functionality.
5. Extend feedback where needed: stable track IDs, loading/error states, selected effect identity, and settings application outcomes.
6. Verify each feature in both directions, including a manual UI change observed by the device when the feature has readable state.
7. Publish a denominator-based coverage report: inventoried capabilities, verified capabilities, and outstanding gaps, separated by command/feedback/UI support. Do not count aliases as independent feature coverage.

A future host adapter may support only a subset. The common AI DJ executor must plan within that host's declared capabilities and explicitly report missing ones. That portability mechanism does not reduce the full Mixxx target.
