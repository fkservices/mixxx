# Live session recording and visual history

> This document was autonomously generated by an AI agent at the user's request. It is a planning draft for human review.

Status: required scope for the Mixxx desktop build. The schema, capture path and UI below are proposed; no recorder, host instrumentation or session viewer is implemented. The [example session](examples/session.example.json) is synthetic design data, not a recording or proof of MIDI support.

## Product behavior

The desktop UI answers: **what is playing, what is the AI trying to do, what did each DJ actually do, and what changed in Mixxx?** It reads the current session live and opens saved sessions with the same timeline. The operator can inspect AI commands, physical-controller gestures, host observations and uncertain origins separately, using musical labels such as “Deck A volume up,” “Treble down,” or “Jog backwards.” Raw MIDI remains available in the event inspector.

A session includes the selected Mixxx playlist snapshot, its occurrence identities, planned order and revisions, actual playback history, three-mode changes, AI intent, MIDI traffic, observed controls and B2B ownership. AI Only records manual input even when AI subsequently overrides it. B2B shows the affected human hold through the current transition, the configurable quiet period and eligibility for a subsequent transition. Playlist Only still records manual performance and AI set organization while emitting no AI performance commands. Disarm remains visible and accessible independently of the selected timeline filter.

Historical playback means **playing the visualization**. Opening, scrubbing or replaying history cannot open an output MIDI port, rearm automation or send old commands to Mixxx. The history viewer may run with Mixxx disconnected.

## Capture boundary and attribution

The required input paths are the AI communicator's outbound/received MIDI and the selected physical controller's ingress to Mixxx. The physical controller remains attached directly to Mixxx. Do not make performance depend on forwarding physical gestures through the AI process.

The first implementation spike must identify an exact source location for an observation hook at Mixxx's MIDI ingress/dispatch boundary, before filtering or mappings can discard messages. The hook needs endpoint instance identity, original bytes, sequence and a monotonic receive timestamp; it must publish asynchronously without synchronous disk writes. A selected mapping integration is acceptable only if evidence proves it captures all messages in the claimed endpoint scope, including unknown and ignored ones. Otherwise it supplies additional semantic/touch hints and does not close SU-02. The current planning research has not verified this hook. Do not assume a second OS MIDI client can tap another client's traffic reliably.

Instrumented mapping dispatch can link a raw message to one or several semantic actions and supported control updates. Shared-control observations alone cannot universally reveal whether AI, a knob, a mouse, keyboard, Mixxx AutoDJ or internal automation caused the value. Add mouse/keyboard origin hints at an identified host input path where feasible; otherwise label the change `unknown` and show the resulting value. An unexplained change can conservatively trigger B2B yield without being falsely recorded as a proven human gesture.

Separate the **producer** that emitted an event from its **actor**: a Mixxx observation hook produces a record of a physical-user event. Store attribution basis such as `captured_endpoint`, `instrumented_dispatch`, `request_correlation` or `unknown`, plus `confirmed`, `inferred` or `unknown` confidence. Matching a recently requested value is evidence of compatibility, not conclusive authorship. A command correlation must not consume or hide simultaneous manual evidence.

Keep raw, semantic and observed events with links rather than merging away their identities. An action group may contain two raw 14-bit CC messages, one decoded gesture and one resulting host observation. Count one gesture in the summary, while showing every byte in the inspector. One message may affect several controls; preserve that fan-out. Host feedback bytes and their decoded observation are representations of one received message, not two physical-user gestures.

The decoder profile contains host/mapping/device versions, channel/address conventions, scaling, units, polarity, relative encoder mode, 14-bit assembly rules and logical control IDs. MIDI channel numbers are 1–16 in the UI; a controller number such as CC 110 is not “channel 110.” An unrecognized message is displayed as raw MIDI with unknown meaning, never assigned a plausible musical label. Assembly timeouts, pair loss, Note On velocity-zero releases and repeated identical values remain recorded.

## Live UI and historical navigation

The main view has a set header (mode, armed state, session health, playlist progress), deck/track lanes, a shared time ruler and a detail panel. Per-deck tracks carry title, occurrence, playback segment, loaded/playing status and source-position marks. The timeline shows Deck A and B overlapping during a transition; EQ, volume, tempo, jog, cue and loop overlays sit on their affected lane. Master volume, crossfader and mode/disarm events have shared lanes. Deck actions with unknown track identity stay visible on the deck rather than being attached to a guessed song.

Observed curves show actual values. Proposed AI curves use a labeled style with their own status; cancelled intent stays distinguishable from a performed move. User gestures and ownership bands show “You controlling bass,” “Held until next transition,” “Pinned manual,” or “Disarmed.” A quiet deadline is an eligibility estimate, not a promise that AI resumes at that instant. B2B resumption additionally requires a later transition start, released input/touch, fresh state, valid generations and a new action starting from the human's value. Quiet expiry alone never permits mid-transition writes.

The detail panel connects intent → queued action → sent MIDI → acceptance → observation, with timestamps and explicit uncertainty. Selecting a raw event shows exact bytes, endpoint and decoder version alongside its semantic label. Unmapped messages, rejected commands, capture gaps and track-identity uncertainty remain searchable. Filtering changes visibility only; it never hides the global disarm or incomplete-recording indicator, and derived session totals identify whether they describe all data or the filtered subset.

History offers play/pause, speed, zoom, time/track navigation and keyboard seeking. “Live” follows the head of the session; inspecting an earlier cursor does not pause performance or recording. Return-to-live is explicit. Text labels and symbols supplement actor colors; focus order reaches filters, track lanes, selected-event detail and disarm. Reduced-motion mode disables animated scrolling while retaining updates.

## JSON session contract

The proposed export contains `schema_version`, `session`, `capture`, `devices`, `mapping_profiles`, `playlist`, `plan_revisions`, `events`, `snapshots`, `playback_segments` and `integrity`. Exact runtime types and JSON Schema are separate implementation deliverables. The [example](examples/session.example.json) fixes illustrative names and relationships, not a final interoperable protocol.

- `session` supplies a unique session ID, wall-clock start, duration, host/app versions and final state. An imported synthetic example is visibly marked as such. Local file references are optional, explicitly local and never assumed present on another machine; raw audio is not embedded.
- `capture` declares precisely which endpoints and event classes were captured, omitted or unavailable, the capture method, clock domains, limits and whether the record is complete. Device reconnect creates a new instance/epoch even if its display name is unchanged.
- Every event has a globally unique ID, monotonically increasing sequence within its producer stream/epoch, session-relative monotonic time, original clock timestamp/domain, actor/attribution and a typed payload. Original stream order is retained. Equal timestamps use stable stream/sequence order for display without asserting a real causal ordering across clocks.
- MIDI records preserve numeric bytes in their received/sent order, direction, endpoint and mapping profile. Semantic events retain message links and normalized or raw units, logical control, deck and track generation when known. AI records add intent/action/session IDs, mode and ownership epochs, status and deadlines. A later observation does not rewrite the earlier request.
- Playlist entries retain stable source occurrence IDs, including duplicates. Plans are revisions of an occurrence order, with pins/edits/reasons. Actual segments reference their occurrence when matched, or explicitly record an external/manual track. Never silently count a manually loaded different track as the expected playlist entry.
- Snapshots store observed state, track identity/generation, mode, armed state, ownership, active playback segments, current plan revision and covered stream cursors. A snapshot is an indexed checkpoint of facts, not permission to emit commands. A gap between it and the requested cursor leaves affected values uncertain.
- Integrity stores observed/captured/persisted/drop counters per stream and queue, gap intervals, reasons, first/last sequence and clean/unclean close. Events or counters lost during a crash produce an unknown interval, not an invented exact drop count. Exported totals reconcile to retained events and declared gaps.

Process and host clocks may differ. Calibrate them, retain mapping/uncertainty samples and include uncertainty in cross-clock latency. Use monotonic time for intervals and the session wall-clock anchor for dates. On process restart, rotate the stream epoch and resynchronize. A backward system-clock adjustment cannot move an event backward in its original monotonic stream. Do not call a round-trip measurement one-way latency.

### Track duration and musical meaning

Record **load**, **transport start**, **position advancement**, **pause/stop**, **unload**, **seek** and **loop** separately. A load is not a play. A play command is not confirmed transport. The runtime profile must freeze the observation criteria for a confirmed playback segment; the example uses confirmed transport plus source-position advancement.

For each segment show elapsed active transport, pauses, source positions and known gaps. Source-position jumps are not elapsed listening time. Looped material may play repeatedly, so elapsed transport can exceed the distinct source range heard. Two simultaneously playing decks have overlapping segment durations; summing them does not equal set wall duration.

“Audible” requires an explicitly labeled criterion. Playback, mixer gain and routing can support an **audibility estimate**, but MIDI cannot prove a listener heard the sound. Confirming audible onset or evaluating a blend requires a separate audio measurement/listening path. JSON may reference an optional local audio recording or prepared waveform data; MIDI carries neither music nor waveforms. Review can show timing/track overlays without an audio file.

End states include completed, interrupted, explicitly skipped, unresolved and still playing at capture end. Session recording ending does not prove that a song stopped. Full-playlist completion uses [the playlist/set rules](PLAN.md), not merely a count of load or start events. The example deliberately records an unfinished excerpt: quiet time expires, but bass remains held until a later transition that is not shown. No reclaimed bass write occurs in the excerpt.

## Persistence, bounds and failures

Use an append-only journal, such as bounded NDJSON chunks, while recording. Store chunk indexes/checkpoints and export a valid JSON object when requested. NDJSON is an internal persistence format, not a mislabeled `.json` export. Atomic checkpoint/export replacement and recoverable complete records protect against a crash in the last write; never amend already saved raw bytes to make a session appear complete.

The MIDI path publishes to a bounded recorder queue without awaiting disk, UI rendering or AI work. Use a separate recorder worker/process and bounded IPC. Persist raw/semantic events at the claimed capture boundary without routine coalescing. UI curves may downsample for display, retaining links to full-resolution records. Coalescing command-generation telemetry does not justify discarding already captured MIDI.

Freeze queue limits, chunk sizes, export/import byte limits and retention policy during the recorder design task; no unbounded buffer is acceptable. Capacity planning must include dense jog/14-bit traffic and returned MIDI. At saturation or disk-full, protect control handling, increment independent drop counters where possible, mark recording degraded, and retain/recover an explicit gap interval. If no storage path remains, show the failure live and persist the failure marker when storage recovers; a crash may leave the final interval unknowable. Do not claim lossless recording in this state or silently discard older sessions. Ending/pausing recording must not stop the music or change ownership mode.

Long sets stream indexed chunks instead of loading the whole journal into memory. Seek loads a compatible preceding snapshot and replays only the needed subsequent events into a visualization state reducer. A checksum/length manifest can detect truncated or mismatched chunks; it does not prove the capture contained every physical event. Export uses a streaming writer, checks available storage and keeps the working journal if export fails.

Validate lengths, event counts, finite numeric values, byte ranges, reference IDs and schema/profile versions. Reject unsupported major schemas before rendering. Render track names and event labels as text; do not evaluate imported scripts, HTML, URLs or MIDI payloads. Historical import is data ingestion only.

## Acceptance scenarios

| Scenario | Required result |
| --- | --- |
| AI raises volume, hardware lowers bass, mouse changes treble. | Live lanes show meaning, actual values and origin evidence. Mouse is labeled mouse only with instrumentation; otherwise unknown. Filters preserve this distinction. |
| Hardware sends identical values, unknown CCs and a 14-bit pair. | Every captured raw message is retained; decoded actions group correctly. The human quiet timer can use repeated input even when the value does not change. |
| AI and human request the same value together. | Both actions remain present; a shared observation does not establish a unique author without stronger evidence. |
| AI queues a bass curve; in B2B the user moves bass at 5.0 s and 5.5 s. | Record cancellation/ownership generation changes, last gesture 5.5 s and quiet eligibility 8.5 s. No bass writes for the rest of that transition, including after 8.5 s. Reclaim only at a later eligible transition start with fresh reconciliation/new intent; other controls may continue. |
| Touch remains held beyond the debounce. | Explicit touch prevents eligibility until release plus quiet time. A value-only controller reports the limitation and cannot claim unchanged contact detection. |
| The same gesture occurs in AI Only, followed by Disarm. | Record bounded AI recovery without a B2B hold; disarm then cancels further recovery and stays latched. |
| Playlist Only user performs the set. | Manual actions/history are recorded; AI emits zero performance messages, and planning alone is not reported as a performed set. |
| Two decks overlap; one seeks or loops. | Lanes and source positions agree with Mixxx; transport, source coverage and wall duration are distinct. |
| Load succeeds but playback never starts, or a track is manually replaced. | No fabricated played duration; correct generation/occurrence and interrupted/unresolved outcome. |
| Open exported history, scrub and change filters. | Same retained facts and snapshots as live; zero output MIDI and no arming, including when Mixxx is running. |
| Slow disk/consumer, dense jog traffic and process crash. | MIDI control remains responsive; visible gaps/counters reconcile where knowable; truncated tail recovery preserves complete records and marks unknown ending. |
| Run the full chosen playlist with a real controller, then reopen it. | Actual order, track durations, intent/actions, ownership and gaps match evidence; retained recording passes stream accounting at the tested load. Audio review assesses the mix separately. |

Split implementation into capture-hook discovery, envelope/schema, raw taps, semantic decoding, journal, recovery, live transport, timeline, filters, history/seek, mode overlays and bounded acceptance tasks. Long-set capture continues in one durable job across worker handoffs; each observer task stays under the project's 30-minute worker limit. A continuous 30-minute recording cannot be replaced with several unrelated short sessions.

## Delegated operational defaults

Capture session data automatically across mode changes and disarm. Pause recording explicitly marks a gap and resume takes a fresh snapshot. Master audio recording is opt-in; microphone/broadcasting never start implicitly. Prepared local waveforms are optional assets, not generated from MIDI. Playback of a historical recording never sends performance MIDI.

Use provisional 16 MiB journal chunks, snapshots no more than 5 seconds apart and query pages of at most 1,000 events. Bound queues/IPC/export separately and benchmark these values before runtime acceptance. The initial tested envelope targets 250 occurrences and 6 hours; capacity is not yet measured. Keep files until deletion by default, with opt-in age/size cleanup and pinned-session protection. Warn on low disk (proposed 5 GiB free); preserve control responsiveness and explicit gaps if storage fails.

Provide notes, ratings, learned-preference inspection/edit/reset, optional recent-history influence (30 days default), and a learning-off switch. Redacted sharing strips unnecessary paths/device identifiers; assets are opt-in. Validate imported versions, sizes and asset paths.
