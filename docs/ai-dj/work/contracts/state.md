## Identity and separate sources of truth

Use F06's `TrackIdentity`, `OccurrenceIdentity`, `DeckPrecondition`, `ActionIdentity`, `ObservationReference` and `ActionAttribution` directly through type imports. A track is the `(libraryId, trackId)` pair. An occurrence is `(setId, occurrenceId, generation)`; two occurrences of one track remain distinct. Unknown occurrence association is the existing explicit null in a loaded deck binding. It does not mean an empty deck. A deck binding cannot be fabricated from a requested load or metadata text.

`DeckObservation.current` observes the entire F06 `DeckPrecondition`, including the deck incarnation, track generation and known loaded/empty binding. Its enclosing deck ID and generation must agree with the observed value. An unknown binding remains an `unknown` observation, never a valid empty precondition. Every replacement, including reloading the same file, changes track generation. Deck recreation changes deck generation. Capability readings tied to a deck carry the exact binding under `deck.kind: known`; an unknown deck context retains its deck ID/incarnation but cannot carry a current `observed` value. Raw values can remain in source diagnostics until binding reconciliation. A null deck denotes a genuinely independent control, never a way to authorize a deck action whose binding is unknown. When a deck binding changes, old readings cannot be relabeled with the new binding.

`RequestedState` is a projection of an existing F06 action's identity and semantic operation, for displaying intent. It grants no execution authority and is never an observed-state message. Sending, host admission and requested values cannot create observations. `InferredIntent` is a separate, uncertain interpretation referencing observations/source events. Its actor and confidence never rewrite actual state or the stronger `ActionAttribution` evidence. Session storage may display all three alongside one another without combining their meanings.

## Observation meanings and freshness

| Status | Meaning and admissible use |
| --- | --- |
| `observed` | Actual host value with observation identity, source event evidence, receipt time and a bounded validity interval. It is current only if all context, identity, presence, ordering and time checks still hold. |
| `stale` | An earlier value retained under `lastKnown`, with its original evidence and an explicit invalidation reason. It is useful for history, never current action authorization. |
| `missing` | Explicit evidence that the named control or instance is absent in this context. It carries no value. Absence remains visible in the capability denominator. |
| `unknown` | No trustworthy value or presence proof exists; includes an unverified existence check, unavailable feedback and unresolved identity. It carries no value. |
| `uncertain` | Evidence exists but conflicts, ordering, clock mapping or binding ambiguity prevent accepting a value. It carries evidence references, not a guessed value. |

`ObservationEvidence` extends F06's `ObservationReference`, allowing outcomes to cite the same observation ID, host/connection and creation revision. Copying an unchanged reading into a later snapshot/delta does not advance its original evidence revision or refresh its timestamps. An observation's host/connection must match its enclosing state context, its revision must not exceed that message's revision, and its clock must match `StateContext.clockId`. An explicitly stale last-known value may reference an old host/connection/clock; consumers cannot use it as a current precondition. After a new stream epoch resets its counters, an explicit `stale` / `stream-gap` value may also retain the old creation revision, which is incomparable to the new stream revision. This exception never applies to `observed` values and does not permit a same-clock receive timestamp in the future. Preserved observation identities and payloads remain immutable.

Use local monotonic milliseconds. Require finite, nonnegative safe-range times, `observedAtMs <= receivedAtMs <= producedAtMs`, and `observedAtMs < validUntilMs`. Validity ends at `validUntilMs`, with a positive lifetime no greater than the capability's `maxAgeMs`; the executor's F06 maximum age and any stricter policy also apply. An `observed` discriminant is not a permanent freshness flag: recheck age at consumption/dispatch. Foreign host timestamps need a proven local clock mapping before they can be used as observation times; otherwise preserve a clock-unmapped uncertainty. Receipt time alone cannot prove a delayed sample was current. Change-only feedback does not stay fresh indefinitely just because no later event arrived; refresh or expire it.

Context includes session, host instance, connection generation, capability revision, exact host/version/build/platform/skin/configuration profile, local clock, and state stream ID/generation. Host restart gets a new host instance. Reconnect changes connection generation. Stream reset changes stream generation or ID; counters never wrap or get reused in the old epoch. Profile or capability changes invalidate affected observations and action preconditions and require a snapshot in the new context. These observations grant no armed state and cannot clear disarm. Catalog definitions are descriptive data, not authority grants.

## Snapshots, deltas and continuity

The state stream is the reconciler's serialized output, not a claim that raw MIDI contains a host sequence number. `sequence` orders messages in one stream epoch; `stateRevision` versions accepted state. Require nonnegative safe integers, stable immutable IDs, and no wrap/reuse. Raw host events must be reconciled before publication; received order alone cannot prove source order or make stale feedback current.

A snapshot atomically replaces the complete projection for its exact context (`replacement: entire-context`). It is not a physical simultaneous host read: individual readings retain their own observation times. Previously cached decks/readings absent from the replacement are discarded; absence from a snapshot supplies no proof of a missing host control. A consumer treats unlisted catalog targets as unknown. A snapshot cannot silently carry values or holds from an old context. `snapshotId` is unique and immutable in its context. A replacement in the same stream requires a newer sequence and revision; a fresh context may start its own counters. No delta is admitted before a baseline snapshot.

A delta names the current baseline `snapshotId`, exact current `baseRevision`, and `previousSequence`. Require `previousSequence` equal to the last accepted sequence, `sequence = previousSequence + 1`, and `stateRevision = baseRevision + 1`. Its full context must match the baseline. Apply all changes atomically after validation, including cross-record deck/instance checks. An empty delta may advance revision but cannot refresh existing observations. A replace change replaces the complete named entry. A remove change targets the exact existing incarnation, with nonempty evidence; it removes a cached entry but is not a numeric zero, proof of an empty deck, or a successful action. Retain explicit missing observations when absence needs to remain visible.

Reject duplicate/conflicting changes to one key and any transaction leaving current readings tied to a replaced/removed deck incarnation. On track replacement, update/remove/invalidate affected readings in that same transaction. Validate the resulting projection; a delta cannot use a previous binding simply because that entry was untouched. Reject mismatched deck IDs/generations, catalog revisions, unknown capability targets, stale instance identities and readings whose value semantics disagree with the catalog.

An identical previously accepted message may be ignored as a duplicate without replay or timestamp refresh. Reusing a message ID or a context/sequence with different content is a conflicting duplicate and produces a gap. Older/out-of-order messages never roll back state. A missing base, unknown snapshot, sequence gap, incompatible context or conflicting duplicate produces `StateContinuityGap`, marks affected current state unusable and requires a fresh snapshot. Do not apply a later delta over the gap, splice old and new contexts, or declare recovery from merely seeing a larger revision. Keep historical evidence, but admission/recovery/essential-feedback disarm belong to later executor/reconciliation cards.

## Manual-control and attribution walkthrough

Its evidence uses `attribution: { actor: "unknown" }`; even a value differing from the AI curve does not prove a human moved a control. Likewise a matching AI requested value or an unlinked send does not establish AI causation. F06 outcome correlation is separate from attribution. If the host does not provide sufficient linkage, retain unknown attribution even when a policy conservatively treats the event as possible manual intervention.
