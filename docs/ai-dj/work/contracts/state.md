## Identity and separate sources of truth

Use F06's `TrackIdentity`, `OccurrenceIdentity`, `DeckPrecondition`, `ActionIdentity`, `ObservationReference` and `ActionAttribution` directly through type imports. A track is the `(libraryId, trackId)` pair. An occurrence is `(setId, occurrenceId, generation)`; two occurrences of one track remain distinct. Unknown occurrence association is the existing explicit null in a loaded deck binding. It does not mean an empty deck. A deck binding cannot be fabricated from a requested load or metadata text.

`DeckObservation.current` observes the entire F06 `DeckPrecondition`, including the deck incarnation, track generation and known loaded/empty binding. Its enclosing deck ID and generation must agree with the observed value. An unknown binding remains an `unknown` observation, never a valid empty precondition. Every replacement, including reloading the same file, changes track generation. Deck recreation changes deck generation. Capability readings tied to a deck carry the exact binding under `deck.kind: known`; an unknown deck context retains its deck ID/incarnation but cannot carry a current `observed` value. Raw values can remain in source diagnostics until binding reconciliation. A null deck denotes a genuinely independent control, never a way to authorize a deck action whose binding is unknown. When a deck binding changes, old readings cannot be relabeled with the new binding.

`RequestedState` is a projection of an existing F06 action's identity and semantic operation, for displaying intent. It grants no execution authority and is never an observed-state message. Sending, host admission and requested values cannot create observations. `InferredIntent` is a separate, uncertain interpretation referencing observations/source events. Its actor and confidence never rewrite actual state or the stronger `ActionAttribution` evidence. Session storage may display all three alongside one another without combining their meanings.

## Observation meanings and freshness

| Status | Meaning and admissible use |
| --- | --- |
| `observed` | Actual host value with observation identity, source event evidence, receipt time and a bounded validity interval. It is current only if all context, identity, presence, ordering and time checks still hold. |
| `stale` | An earlier value retained under `lastKnown`, with its original evidence and an explicit invalidation reason. It is useful for history, never current action authorization. |
| `missing` | Explicit evidence that the named control or instance is absent in this context. It carries no value. Absence remains visible in the capability denominator. |
| `unknown` | No trustworthy value or presence proof exists; includes an unverified existence check, unavailable feedback and unresolved identity. It carries no value. |
| `uncertain` | Evidence exists but conflicts, ordering, clock mapping or binding ambiguity prevent accepting a value. It carries evidence references, not a guessed value. |

`ObservationEvidence` extends F06's `ObservationReference`, allowing outcomes to cite the same observation ID, host/connection and creation revision. Copying an unchanged reading into a later snapshot/delta does not advance its original evidence revision or refresh its timestamps. An observation's host/connection must match its enclosing state context, its revision must not exceed that message's revision, and its clock must match `StateContext.clockId`. An explicitly stale last-known value may reference an old host/connection/clock; consumers cannot use it as a current precondition.

Use local monotonic milliseconds. Require finite, nonnegative safe-range times, `observedAtMs <= receivedAtMs <= producedAtMs`, and `observedAtMs < validUntilMs`. Validity ends at `validUntilMs`, with a positive lifetime no greater than the capability's `maxAgeMs`; the executor's F06 maximum age and any stricter policy also apply. An `observed` discriminant is not a permanent freshness flag: recheck age at consumption/dispatch. Foreign host timestamps need a proven local clock mapping before they can be used as observation times; otherwise preserve a clock-unmapped uncertainty. Receipt time alone cannot prove a delayed sample was current. Change-only feedback does not stay fresh indefinitely just because no later event arrived; refresh or expire it.

Context includes session, host instance, connection generation, capability revision, exact host/version/build/platform/skin/configuration profile, local clock, and state stream ID/generation. Host restart gets a new host instance. Reconnect changes connection generation. Stream reset changes stream generation or ID; counters never wrap or get reused in the old epoch. Profile or capability changes invalidate affected observations and action preconditions and require a snapshot in the new context. These observations grant no armed state and cannot clear disarm. Catalog definitions are descriptive data, not authority grants.

## Canonical capabilities and evidence

`CapabilityId` has the `mixxx.` prefix and identifies one semantic feature, independent of host alias or instance address. F08 must require nonempty ASCII IDs under F06's 128-byte opaque-ID rules; the suffix must be nonempty. Catalog records are keyed by canonical ID. An alias is a one-hop lookup to an existing canonical definition in the same profile; it is not another definition, instance or evidence record. Reject duplicate IDs, alias collisions, alias chains/cycles, dangling references and aliases with unproven semantic equivalence. Similar names or numerically equal readings do not establish an alias.

Example: a hypothetical validated profile lists `mixxx.deck.playing` once and maps alias IDs `Channel1.play` and `deck1.playing` to it. There is **one canonical feature** in this example, regardless of its two aliases. Deck 1 and deck 2 are separate dynamic instances with separate presence/behavior evidence. A deck-1 pass does not establish deck-2 coverage. These aliases are synthetic examples, not a claim that an actual profile has been verified.

`FeatureFamily` preserves all 22 accepted families from [the coverage plan](../../CONTROL-COVERAGE.md). `CapabilityDefinition.status` is specification progress, not runtime support. Unknown, absent, unresolved and extension-needed definitions remain in the denominator. An open inventory or incomplete dynamic enumeration means the full denominator is not yet known: report a known lower bound and the unresolved scope, never a complete percentage or a fabricated zero total. F10 and inventory cards own pagination and evidence-backed closure; this contract does not enumerate all controls.

`HostProfile` freezes the exact version/build/platform, skin revision and configuration. Changed effect selection, configured deck counts, instance creation/removal, or other changes affecting control meaning require an updated catalog revision. `CapabilityInstance` identifies a particular deck/slot/parameter/service incarnation and its parent incarnation; `definitionId` identifies the selected effect or other instance definition. Reusing a slot for a different effect changes its generation and definition ID even when its UI position is unchanged. A changed parent invalidates children. Every dynamic reference must exactly match a discovered instance in that definition's current catalog. Singleton targets use null. Unknown enumeration retains discovered instances and an explicit continuation; an empty discovered list alone never means complete or unsupported.

Read semantics distinguish state, not-readable and unresolved. State declares the value shape, delivery mechanism, maximum age and required explicit presence. Numeric values carry units, finite physical/normalized ranges, optional quantization step, tolerance, optional neutral value and a profile mapping ID. Require `minimum <= maximum`, nonnegative tolerance, positive step when non-null, and a neutral value within range when specified. No default EQ center/gain is inferred. Readings must match the exact declared kind, unit, range and enum choices. Track and occurrence values reuse F06 identities. Metadata strings and richer service results are not smuggled through an enum or arbitrary JSON escape hatch; later contracts must add a versioned shape if needed.

Write semantics distinguish unresolved, read-only, extension-needed and a binding to the **closed F06 action union**. `ActionSelector` identifies exact deck/mixer parameters where needed. The behavior must match F06: setters are desired-state; cue goto/load are triggers; cue press/release are momentary; jog is relative. A command mapping cannot broaden a setter into a toggle. A mapping/spec ID is an opaque reference to reviewed adapter data, never a callable script, group/key name, function or arbitrary operation. `extension-needed.operationSpecId` records missing future work and cannot execute. Conventional MIDI must declare no request-linked acknowledgement or deduplication unless an actual implemented protocol provides it. Declared semantics and successful sends alone do not prove capabilities.

`CapabilityAssessment` has independent availability plus four independent dimensions:

| Dimension | A passed result requires |
| --- | --- |
| `command` | Evidence of actual host command behavior, not just an outbound send or a source declaration. |
| `feedback` | Actual host feedback evidence, including applicable manual-change/read behavior and valid presence. |
| `nativeUi` | Observed corresponding native Mixxx UI in the named skin/configuration. A local mock/UI is insufficient. |
| `runtime` | The actual scenario's acceptance evidence, including its required host/device/audio/timing checks. Passing other dimensions does not imply this pass. |

Each pass/failure has nonempty evidence references identifying run, artifact, time, exact profile/host/context and capability/instance. A reference must resolve to retained evidence; IDs alone are not proof. Results from another profile/instance do not count toward the current target. `not-applicable` requires a concrete rationale and explicit review evidence; keep it separate from passes and in denominator reporting. It cannot remove a required UI/runtime gate. Missing assessments are untested, never supported. Report each dimension independently over unique canonical features, plus required instance completion separately. A family closes only after all known required capabilities, dynamic instances, unknown scopes and acceptance gates are resolved by evidence.

Example: an effect parameter may be present with command and feedback passed, native UI untested, runtime failed, and a different unenumerated effect slot outstanding. This is partial evidence for one instance, not full effects coverage. A sampler-bank operation whose current surface opens a dialog can remain extension-needed with a bounded operation spec ID; its successful trigger does not prove a selected file was loaded.

## Snapshots, deltas and continuity

The state stream is the reconciler's serialized output, not a claim that raw MIDI contains a host sequence number. `sequence` orders messages in one stream epoch; `stateRevision` versions accepted state. Require nonnegative safe integers, stable immutable IDs, and no wrap/reuse. Raw host events must be reconciled before publication; received order alone cannot prove source order or make stale feedback current.

A snapshot atomically replaces the complete projection for its exact context (`replacement: entire-context`). It is not a physical simultaneous host read: individual readings retain their own observation times. Previously cached decks/readings absent from the replacement are discarded; absence from a snapshot supplies no proof of a missing host control. A consumer treats unlisted catalog targets as unknown. A snapshot cannot silently carry values or holds from an old context. `snapshotId` is unique and immutable in its context. A replacement in the same stream requires a newer sequence and revision; a fresh context may start its own counters. No delta is admitted before a baseline snapshot.

A delta names the current baseline `snapshotId`, exact current `baseRevision`, and `previousSequence`. Require `previousSequence` equal to the last accepted sequence, `sequence = previousSequence + 1`, and `stateRevision = baseRevision + 1`. Its full context must match the baseline. Apply all changes atomically after validation, including cross-record deck/instance checks. An empty delta may advance revision but cannot refresh existing observations. A replace change replaces the complete named entry. A remove change targets the exact existing incarnation, with nonempty evidence; it removes a cached entry but is not a numeric zero, proof of an empty deck, or a successful action. Retain explicit missing observations when absence needs to remain visible.

Reject duplicate/conflicting changes to one key and any transaction leaving current readings tied to a replaced/removed deck incarnation. On track replacement, update/remove/invalidate affected readings in that same transaction. Validate the resulting projection; a delta cannot use a previous binding simply because that entry was untouched. Reject mismatched deck IDs/generations, catalog revisions, unknown capability targets, stale instance identities and readings whose value semantics disagree with the catalog.

An identical previously accepted message may be ignored as a duplicate without replay or timestamp refresh. Reusing a message ID or a context/sequence with different content is a conflicting duplicate and produces a gap. Older/out-of-order messages never roll back state. A missing base, unknown snapshot, sequence gap, incompatible context or conflicting duplicate produces `StateContinuityGap`, marks affected current state unusable and requires a fresh snapshot. Do not apply a later delta over the gap, splice old and new contexts, or declare recovery from merely seeing a larger revision. Keep historical evidence, but admission/recovery/essential-feedback disarm belong to later executor/reconciliation cards.

## Manual-control and attribution walkthrough

Host feedback reports volume 0.4 for the current deck. It proves an actual value only when its normal presence/binding/freshness checks pass. Its evidence uses `attribution: { actor: "unknown" }`; even a value differing from the AI curve does not prove a human moved a control. A separate `InferredIntent` may reference it with `interpretation: manual-adjustment`, `inferredActor: human`, and confidence 0.6. That remains inference and must be labeled as such.

A captured physical-controller event with a reliable source identity establishes human input, but pickup/soft takeover may mean it caused no host change. Only evidence actually linking the source event to the particular observed change permits `ActionAttribution` with `actor: human`, `sourceId` and `evidenceEventId`. Likewise a matching AI requested value or an unlinked send does not establish AI causation. F06 outcome correlation is separate from attribution. If the host does not provide sufficient linkage, retain unknown attribution even when a policy conservatively treats the event as possible manual intervention.

Known human pause/stop or track replacement observations can inform later B2B hold logic; these data types do not implement it. Actual state remains visible in AIOnly, B2B and PlaylistOnly. Mode policy cannot overwrite a human value in the observed projection, and inferred intent cannot establish a persistent preference without the later learning/provenance rules.
