This contract defines the version-1 data exported by [actions.ts](../../../../ai-dj/core/actions.ts). It implements no executor, validator, host adapter, state store or ownership policy. TypeScript types describe admitted data; they do not validate untrusted JSON. F08 must implement independent runtime validation. F07 owns the observed-state and capability schemas; the small identity/precondition/observation references here are boundaries to integrate with those schemas, not replacement snapshots.

## Envelope, identity and limits

An action has a session ID, action ID and safe-integer sequence, a schema version, monotonic timing, authoritative-state preconditions, and exactly one operation/authority pair. IDs identify data; they never identify JavaScript functions, scripts, filesystem paths or arbitrary host control names. The same session/action ID and session/sequence must resolve to exactly one immutable payload. Reusing either with different data is invalid. Attempts receive separate IDs. Restart or reconnect invalidates queued work; a new connection generation does not make old commands replayable.

Track identity consists of library and track IDs. A playlist occurrence has set ID, occurrence ID and generation, so two occurrences of one file remain distinct. A deck reference also carries deck incarnation and track generations. An empty deck is explicit; an unknown binding cannot authorize work. A loaded human/library track may have a null occurrence pending set reconciliation, without inventing a playlist association. Every load or manual replacement, including loading the same file again, changes track generation. Deck recreation changes deck generation. Current preconditions describe the previous deck binding; load arguments describe the intended new track and occurrence.

`ACTION_LIMITS` sets version-1 admission ceilings. Runtime checks must enforce every ceiling and cross-field rule below; these are new contract bounds, not measured host limits. A negotiated capability, user policy or executor may impose tighter limits. Longer sets and transitions submit bounded actions nearer their execution time; these limits do not cap set duration.

Deck operations require exactly one matching target deck precondition plus any independently required dependent decks. Playing, cue and jog require a known loaded binding. Load requires a current binding (loaded or empty), a valid destination identity/occurrence, and a `deck-silent` condition on the destination. Cue operations require a known main cue for the expected track. Extra host conditions can restrict an operation but never override mandatory conditions. `deck-playing` is an exact precondition, `deck-silent` requires trustworthy audibility evidence, and `cue-available` requires the known marker. Neither a zero fader nor successful loading alone proves audible participation in a set.

## Closed operation meanings

| Operation | Kind and meaning | Required ownership and outcome |
| --- | --- | --- |
| `deck.set_playing` | Desired-state boolean; never a toggle. | Deck transport; observe the actual playing state on the expected binding. Already-satisfied state needs a fresh observation, even if no change event fires. |
| `deck.set_parameter` | Desired-state absolute volume or low/mid/high EQ value. | Exact deck parameter; observe mapped value within capability tolerance. |
| `mixer.set_parameter` | Desired-state absolute crossfader value. | Exact mixer parameter; observe mapped value within capability tolerance. |
| `deck.cue_goto` | One trigger to seek to the current main cue without intentionally starting playback. It must not be mapped to a toggle or a hold. | Cue, jog and transport; verify cue/playhead and unchanged playing state for that track. A profile lacking this exact behavior is unsupported. |
| `deck.load_track` | One load attempt by stable library/track ID for a particular occurrence. Classified as a trigger even when loading the same file. | Track, transport, cue and jog; confirm intended host track identity and a new track generation. Local occurrence association also requires successful reconciliation. Loading never marks an occurrence played. |
| `deck.cue_press` | Start one main-cue hold under a unique press lease. | Cue, jog and transport; observe/acknowledge the particular active hold and retain its release obligation. |
| `deck.cue_release` | End only the hold identified by the matching lease. | The release obligation grants narrow cleanup authority; observe that hold released. It cannot release a newer human/AI press. |
| `deck.jog` | Apply one signed relative displacement in beats. | Jog and transport; reconcile actual playhead behavior against baseline and intervening playback. A value resembling the expected position alone cannot establish who caused it. |

Desired-state retry is only potentially safe: first reconcile a trustworthy current state and recheck deadlines, mode, authority, plan, track identity/generation and capability. A retry of the identical admitted request retains action/session/sequence identity with a new attempt ID and supported host deduplication. A fresh plan produces a fresh action. Unsupported correlation/deduplication may rule out retries even for setters. No trigger, press or relative operation permits blind retry after an uncertain send or acknowledgement. A load error may follow a successful load; reconcile identity before any new attempt. There is no caller-controlled `retrySafe` flag.

## Cancellation, modes and release obligations

Performance authority includes mode, arming and authority generations, immutable plan identity/revision, cancellation group/generation, transition identity/generation/ordinal, and exact ownership grants. These are assertions against the executor's authoritative registry, not tokens that a planner can mint to authorize itself. A null transition means independent work outside a transition, not a synthetic transition boundary. Capability guards and current host/authority state can always reject an otherwise well-shaped request.

Only AIOnly and B2B occur in `PerformanceAuthority`. PlaylistOnly cannot carry a performance action; planning/read access and explicit playlist saving use later contracts. AIOnly ordinary manual changes can cause fresh bounded recovery while armed. In B2B, invalidate affected grants immediately on human input; preserve holds for the rest of the actual current transition. Continued input resets the default 3-second quiet interval. Reclaim only at a later real transition start after release, quiet expiry and fresh reconciliation, with a new grant and plan from the human value. A bar boundary, elapsed timer, new request ID or null transition cannot bypass a hold. Input without touch evidence remains an inference; feedback alone does not identify the actor.

Manual Pause/Stop creates a latched B2B transport hold that also blocks dependent cue/load/jog actions until human playback or explicit release. Global disarm stays latched through mode changes; restart/transport loss requires deliberate rearm. Mode switches invalidate old work, including already-armed AIOnly/B2B switches that otherwise continue without another Start. Manual replacement invalidates the old track generation and dependent plan actions, preserves human holds, and replans around the new identity. It cannot silently restore the previous choice or mark the displaced occurrence played. Later state/authority modules implement these mechanisms; F06 only carries their checks and cancellation reasons.

Before sending a press, the executor must register a bounded release obligation and establish a host-supported watchdog/lease path. Its identity binds the session, host instance/connection, deck/track generations, control, press action and press generation. An accepted request alone does not establish an active hold: `acknowledged-active` requires explicit host evidence of that particular hold. A `sent-unconfirmed` obligation remains unresolved and permits only a verified lease-scoped cleanup path; it never proves that a press occurred.

A cue release uses `ReleaseCleanupAuthority`, with a lease exactly matching its operation. Normal cancellation, human takeover, disarm and PlaylistOnly must not suppress cleanup of an outstanding AI hold. Release does not inherit the cancelled performance grant or revive any plan. The release obligation is authoritative; all host/deck/track/press lease bindings must still match. It is not a broad permission to send arbitrary note-off messages. If the binding changed, reconcile the obligation with the host/watchdog; reject a stale release against a new track or press. Release is idempotent only for the same verified lease and cannot retry the original press. The host watchdog must retire that lease on expiry or binding replacement. If lease identity/current state cannot be established, record `release-unconfirmed` and keep the outstanding cleanup visible; do not claim success. F06 defines this obligation, not its watchdog implementation or runtime proof.

## Outcome evidence

`ActionOutcome` is an append-only evidence event union. It is not a linear state machine whose successive labels imply completion. Events have separate event and action identities, monotonic timestamps and explicit stages:

- `requested`: intent exists; nothing has been sent.
- `sent`: a known transport submission occurred, with its attempt/message IDs. It proves no host acceptance or effect. A send whose result is unknown uses `uncertain`.
- `accepted`: the host explicitly admitted this request, with a receipt and attempt. It proves no postcondition. Conventional MIDI output cannot fabricate this evidence.
- `observed`: a fresh actual host observation satisfies or fails the operation's defined condition. It references F07 state evidence instead of replacing it with requested values. `state-only` correlation does not establish causation; `request-linked` requires an actual host receipt link. Actor attribution separately requires source-event evidence, even with correlation. Default to unknown.
- `uncertain`: the possible effect remains unresolved (including absent acceptance, lost feedback, timeout, ambiguous correlation or unconfirmed release); this is not a retry instruction.
- `rejected`, `cancelled`, `expired`: identify the failed admission or cancelled/late future work. They cannot retract an already-sent side effect. After dispatch, observation expiry also requires uncertainty/reconciliation. Observations can arrive after cancellation or expiry and must still be recorded without reviving the command.

There need not be an accepted event before an observed event. Fresh already-satisfied state may require no send. Duplicate/out-of-order events reconcile by identity and evidence rather than a numeric status ranking. Neither observed playing nor loading proves a completed transition, audible musical participation, native UI proof or human listening quality. Session/set contracts own those separate outcomes.

## Example walks and future expansion

1. **Play:** session `s1`, action `a1`, sequence 1, deck `d1` generation 2/track generation 7, library `lib1` track `t1`, occurrence `o1` generation 0. Request `deck.set_playing` with true under the current transport grant. `sent` then `accepted` remains pending; fresh observed playing true satisfies the condition. If a human reloads the same file and track generation becomes 8, the old request cannot be emitted/retried. A second occurrence `o2` is not `o1`.
2. **Cue:** `deck.cue_goto` is a one-shot trigger; an acknowledgement timeout does not authorize replay. For a held cue, `deck.cue_press` uses its own action ID in lease `hold1`/press generation 4 and a bounded release deadline. A separate release action references that exact lease. Disarm cancels performance while cleanup remains eligible; a new press generation 5 or replacement track invalidates the stale release. Missing release confirmation remains uncertain.
3. **Load:** action `a3` expects destination deck `d2` empty at track generation 10 and silent, then requests `(lib1,t1,o2)`. Sending and acceptance do not establish a load. Only fresh host identity `t1` with new track generation and reconciled occurrence association supports success. If a manual track arrives first, cancel/replan; do not restore `t1`. The original occurrence remains accounted for even when displaced.
4. **Relative jog:** action `a4` requests `delta: -0.25`, `unit: beats` against the current loaded track/position snapshot and jog/transport grants. Apply once; after ambiguous output, observe and reconcile rather than repeating a backward move. Reject `NaN`, infinities, zero and `4.01`. Absolute fader value `0.25` belongs to a desired-state operation and is never this delta.
