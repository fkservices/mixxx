# P09 — Durable local set archive

> Autonomously AI-generated implementation evidence at the user's request.

`ai-dj/sets/store.ts` stores content-addressed source snapshots separately from append-only set revisions. A revision contains the set definition, planned order and actual history/outcomes. A current-revision pointer advances in the same SQLite transaction as the source and revision inserts. Expected storage revision provides compare-and-swap protection across separate database connections; it is distinct from musical set/plan/history revisions.

All previous revisions remain readable. Sources are never updated through this API. An identical canonical JSON source reuses its hash; a changed source is a separate archived object. Hashes on both source and revision payload detect accidental content changes. Unsupported database application IDs/versions are refused before companion tables are added. This opens only the explicitly supplied companion database, and refuses an unrelated library database.

Recovery returns JSON fields as **unknown**, with `disarmed-reconciliation-required`. It does not cast disk content into trusted runtime state, arm automation, call a host, or restore a session token. Saving checks serializable bounded data and matching set context, but is not the full musical invariant validator. The later admission/reconciliation/reducer tasks must validate source/occurrence relationships, transition legality, terminal evidence and fresh host state before use. The saved interruption and unknown-outcome records remain intact rather than being converted to played/skipped.

The implementation uses the configured Node runtime's built-in SQLite module, verified locally and checked against [Node's API documentation](https://nodejs.org/api/sqlite.html). Writes use `BEGIN IMMEDIATE`, WAL and `synchronous=FULL`, with a one-second busy timeout. The API is synchronous and must be used outside the time-critical MIDI loop when integrated. This task introduces no calls from that loop. Sources and revision payloads each have a 16 MiB bound; plain JSON traversal also has depth/node limits. Capacity errors never truncate saved data.
