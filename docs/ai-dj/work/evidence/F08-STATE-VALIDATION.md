## Reference data contract

The unchecked `resolveCapability` callback and header-only baseline were removed. `StateValidationReferences` now accepts plain bounded JSON data:

- `catalog`: `StateCatalogReference`, schema version 1, exact `CapabilityContext` including every `HostProfile` field, `catalogId`, current instance inventory, exact canonical target resolutions, deck declarations and a retained evidence-ID index.
- Each target resolution includes the complete `CapabilityReference`, F07 read semantics/value shape, explicit availability evidence and its applicable deck incarnation or explicit null for an independent control. Each current instance must match its inventory record including generation, kind, parent and definition; parents must exist in the same inventory and form an acyclic graph. One canonical capability cannot claim conflicting read/singleton/dynamic definitions.
- Each deck declaration includes exact deck identity/incarnation, explicit availability and a positive maximum observation age. Known empty bindings are valid data. Unknown binding cannot carry a current observed reading.
- Optional `baseline` is the **complete last accepted projection** as a `StateSnapshot`, including its current sequence/message ID/revision, all decks and all readings. For a context-changing replacement snapshot, `baselineCatalog` supplies the old catalog needed to validate that full baseline. A same-catalog baseline always uses the current catalog rules, so a supplied historical projection cannot weaken them.

These references come from the trusted catalog/reconciler, separately from the incoming state message. The fixed reference wrapper permits at most three components, checks its prototype and own descriptors without invoking getters, and rejects hidden/symbol/unknown fields. Each catalog, baseline and historical catalog is independently copied/frozen and bounded to 65,536 bytes / 4,096 nodes before use; the combined three-component bundle may exceed a single transport limit without weakening any component limit. Components reject accessors/functions/unknown fields and undergo their own bounded validation. The validator checks their target/context consistency rather than trusting an unchecked callback's return value. This is a **strict current-catalog projection interface**, not an entry point for arbitrary raw `CapabilityCatalog` definitions, aliases, assessments or inventory-closure claims. Catalog production/discovery and retained evidence storage remain their owners' work. Retained IDs are checked against the supplied trusted index; this pure function performs no evidence-store I/O and cannot independently prove that a host event occurred.

Initial snapshots require catalog data even when their deck/reading arrays are empty. Omission of a catalog target from a full snapshot means no cached reading; it is not fabricated absence. A caller with an existing baseline must supply it. Supplying no baseline represents a fresh context at the trusted caller boundary, not permission for a sender to bypass lineage.

## Admission behavior

| Area | Implemented checks |
| --- | --- |
| Observation shape | Correct generic value validator for deck preconditions versus capability values; exact variants and fields; invalid/unknown payload kinds reject |
| Current evidence | Matching host/connection/clock; bounded positive lifetime; retained source-event references; matching creation revision; comparable timestamps cannot be in the future; current values must still be valid at message production |
| Historical evidence | Explicit stale values may preserve an old host, connection, revision or clock; incomparable old-clock timestamps are not compared to the new clock. A `profile-changed` historical value retains its structurally valid old kind/unit without claiming agreement with the current profile. Explicit stale `stream-gap` evidence does not compare its prior creation revision against the new stream's counter, because frozen F07 evidence does not carry a stream epoch. Same-clock received timestamps still cannot be in the future, observed values retain the revision check, and supplied-baseline immutable-payload/resurrection checks remain. This supports a reset snapshot followed by a delta without upgrading stale evidence to current state |
| Presence | Current values require target-specific present evidence; missing requires the same target's retained absence evidence. Zero/false alone cannot establish presence |
| Value meanings | Exact declared kind/unit/range/enum membership, normalized `[0,1]`, finite bounds, nonnegative tolerance, positive optional step and in-range optional neutral value |
| Identities | Nonempty `mixxx.` suffix; exact canonical target and complete current instance identity; current parent generations/definitions; explicit applicable deck; exact current loaded/empty precondition for known readings |
| Snapshots | Full projection validation; one deck ID regardless of generation and one canonical target/instance ID regardless of object key order; replacement lineage and immutable observation identities |
| Deltas | Immediate safe sequence/revision lineage and full profile/context/baseline match; one change per logical key; removal of exact existing incarnations with retained evidence; complete resulting projection checked including untouched readings |
| Replacement/invalidation | Changed loaded-track identity or loaded/empty status requires a new track generation; reconciled occurrence association alone preserves the track generation but still requires matching replacement readings; unchanged old readings fail after deck replacement/removal. Updating, removing or explicitly making the affected reading stale in the same transaction is supported. Instance meaning/incarnation changes require a new catalog context and snapshot |
| Evidence identity | Reusing an observation identity with altered value, owner, binding, timestamps or evidence rejects. Stale or old-context evidence cannot become current again under the same identity. An unchanged observation keeps its original age/revision |
| Epochs | A profile/catalog change cannot reset counters inside an unchanged stream epoch. New stream epochs may establish new counters; connection, capability, same-stream and same-profile generation regressions reject where comparable |
| Capacity | Existing transport/key/node/depth/string/collection bounds apply to input, references, full baseline and full candidate projection. A delta cannot grow a projection beyond the limit just because its own message fits |
